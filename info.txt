Continúa con el PASO 4: adaptadores e infraestructura del Servicio de Pedidos (`services/orders-service`), basándote en `docs/SDD.md`, `docs/SOLID.md`, el dominio, los puertos y los casos de uso ya implementados. Esta fase deja el servicio funcionando de punta a punta por HTTP, con MongoDB real y con los otros servicios simulados.

## Alcance
No incluyas: integración al `docker-compose.yml` (es la subtarea 6) ni el API Gateway.

## 1. Persistencia con MongoDB (Mongoose)
- Schemas `carts` y `orders` según el SDD (ítems incrustados, snapshot de nombre/precio/moneda/cantidad) y mappers explícitos entre schema y dominio (usa la reconstitución de entidades que ya existe). El dominio NO debe importar Mongoose.
- Implementa `CartRepository` y `OrderRepository` como adaptadores.
- Índices: carrito único por `userId`; órdenes por `userId + createdAt` y por `status`; índice ÚNICO por `userId + idempotencyKey` (parcial, solo cuando exista la clave) para garantizar atómicamente una orden por clave; y almacenamiento con índice único para deduplicar eventos de pago por `eventId`.
- Maneja el error de clave duplicada de Mongo traduciéndolo al comportamiento definido en el caso de uso (devolver la orden original), sin filtrar detalles de Mongo.
- Convención de ids: documenta la que uses (ObjectId o UUID) y déjala como SUPUESTO.

## 2. Capa HTTP
- DTOs con class-validator y class-transformer, y decoradores de Swagger (`@ApiTags`, `@ApiOperation`, ejemplos de request/response y errores) para TODOS los endpoints del SDD: carrito, órdenes, `payment-result` (interno) y administración.
- Controladores delgados: solo validan, llaman al caso de uso y mapean la respuesta. Sin lógica de negocio.
- Cabecera `Idempotency-Key` en `POST /api/orders`.
- Paginación y filtro por estado en `GET /api/orders` y `GET /api/admin/orders`.
- Filtro global de excepciones que traduzca errores de dominio/aplicación a códigos HTTP (400, 401, 403, 404, 409, 422, 502/503) con un formato de error único, como define el SDD.

## 3. Autenticación y autorización
- Guard JWT que valide el token y tome `userId` y `role`. ANTES de implementarlo, revisa cómo emite y valida el JWT el servicio de Usuarios en la rama `origin/dev/users-service` (algoritmo, claims, secreto/clave pública, variables de entorno) y alinéate. Si no está definido, usa configuración por variables de entorno y márcalo como SUPUESTO.
- Guard de roles para los endpoints de administración.
- Endpoint interno `POST /api/orders/:id/payment-result`: autenticación entre servicios mediante una API key/secreto compartido en cabecera (configurable por variable de entorno), distinta del JWT de usuario. Documéntalo como SUPUESTO hasta que se acuerde con Pagos.

## 4. Adaptadores de servicios externos
Implementa `UserServicePort`, `CatalogServicePort` y `PaymentServicePort` con DOS variantes cada uno, seleccionables por variable de entorno (por ejemplo `USERS_ADAPTER=http|stub`):
- **HTTP** (`@nestjs/axios` o `fetch`): URL base por variable de entorno, timeouts, reintentos limitados solo en operaciones idempotentes, traducción de errores a `ExternalServiceUnavailableError`, propagación de un `X-Request-Id` y manejo de respuestas inesperadas. El contrato (rutas, cuerpos) sale del SDD; márcalo como SUPUESTO hasta que mis compañeros publiquen sus APIs.
- **Stub/mock** para desarrollo local y pruebas: catálogo con productos de ejemplo y stock, pagos que pueden aprobar o rechazar de forma configurable, usuarios con un par de usuarios de prueba.
- También implementa `ClockPort` e `IdGeneratorPort`.

## 5. Módulos y configuración
- Cablea todo con módulos de NestJS usando los tokens de inyección de los puertos (módulo de carrito, de órdenes, de adaptadores y de configuración).
- Validación de variables de entorno al arrancar (falla rápido si falta algo crítico) y actualiza `.env.example` con TODAS las variables nuevas (Mongo, JWT, URLs de servicios, API key interna, selección de adaptadores, timeouts).
- Mantén `GET /api/health` y Swagger en `/docs`.

## 6. Pruebas
- Integración de repositorios contra MongoDB real (usa `mongodb-memory-server` o un contenedor de prueba, lo que funcione mejor aquí; Docker ya está disponible): unicidad de carrito, índice de idempotencia, deduplicación de eventos de pago, paginación y filtros.
- Pruebas de los adaptadores HTTP con un servidor simulado (por ejemplo `msw` o `nock`): timeouts, errores 5xx, reintentos y traducción de errores.
- Pruebas e2e con `supertest` de los flujos principales usando adaptadores stub: agregar ítems → checkout → pago aprobado; checkout con pago rechazado (compensación); checkout idempotente (misma clave, una sola orden); acceso a órdenes ajenas (403/404); endpoint interno sin API key (401); rutas de administración con rol incorrecto (403); validaciones 400.
